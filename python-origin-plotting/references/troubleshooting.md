# 有界排障与本机实测

## 原生文字替代法已验证（2026-09-30）

同一软件环境下，普通图形文字仍有上划线，但原生散点的数据标签正常。在透明的全页坐标图层中，用单点散点的自定义标签重建标题、轴说明、图例文字和面板号，原普通文字仅隐藏。四张论文图共80个文字对象已替代；保存、独立重开后，PNG、PDF和SVG实际渲染均无上划线，74张原数据表及原科学曲线绑定核验未变。方法与可执行代码片段见[原生数据标签替代法](native-text-workaround.md)。

这是本机验证的渲染替代方法，不是软件底层根因修复。后续版本或不同文字仍需单页验收。旧正常实例方案及失败记录保留如下，避免把曾经局部成功的方法误认成通用修复。

## 已观测案例（2026-09-29，不是所有电脑的普遍结论）

环境：OriginPro 2024 10.100178、originpro 1.1.15、OriginExt 1.2.5。论文统计小表生成OPJU后，独立COM导出的轴标题和普通文字出现上划线，刻度数字正常。去掉论文样式、换Origin/Line自带模板、API/LabTalk普通文字、Arial/去边框均复现；原字符串没有`\ab`。

**用户在正常手动Origin里打开同一最小OPJU时没有上划线；后续两张演变图的正常实例PNG/PDF导出也通过了目视检查。** 但同实例的另三张旧图仍有上划线，根因尚未完整定位。不能据网络论坛案例判定本机许可异常，也不能把手动屏幕正常或单页成功等同于所有工程、格式均正常。

### 正常实例：部分图件已验证的导出路径

1. 用户正常启动Origin，确认目标实例、当前工作簿和已有图页。外部Python直接`op.attach()`，不创建新项目。
2. 对已审查工程使用`doc -a`追加，不覆盖用户项目；已有图页无需再次追加。读取实际图页名。
3. 激活图页，`doc -uw;`，用工作流中的`expgraph -sw`导出到新目录。导出后`op.detach()`，不保存整个用户项目、不关闭Origin。
4. 分别检查PNG与PDF实际渲染。2026-09-29实测：`EvolutionG`和`EvolutionGT`六面板图无上划线，G另获用户确认。SVG已导出，但不能由PNG通过直接认定SVG视觉通过。

**适用范围与停止条件：** 同一正常实例内，`Risk`、`Anchors`、`PhaseThermal`仍异常。Risk分别经`doc -afr`与`doc -a`载入、`draw -uwi`强制重画、原样重设标签文字后，SVG/PDF哈希均未变化。因此这些命令不是已验证的消除上划线的方法；不要循环重复，也不要据此归因为缓存。记录每图实际状态，保留已干净的图，不用异常导出替换原来的正常阅读版。

处理方式：保留正确的原生工作表/图层与源值；将自动导出标为预览；在正常实例检查最终导出后再替换主图。不要移除SVG线条来掩盖未定位问题，不修改许可、私钥、注册表或用户原工程。不要反复让用户核查已确认正常的同一项。

## 最小诊断顺序

1. 保留失败图、输入字符串、版本和错误信息；创建不含研究数据的小工程。
2. 比较普通字/轴标题与刻度数字；分别检查工程屏幕显示和PNG/SVG/PDF；使用同一工程比较手动与自动实例。
3. 每个独立假设做一次有界测试；连续同一失败不循环启动实例。无法进一步定位时交付原生工程并准确标注未完成的导出检查。
4. 修复尺寸、标签换行等已明确的独立问题，不借机更改科研结果。
